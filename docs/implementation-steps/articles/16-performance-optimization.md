# 从 547KB 入口到按需加载：Begin Agent 的一次性能优化

功能逐步补齐以后，系统的启动成本也在增长。一个还停留在登录页的用户，会先下载任务、编辑器、管理页面、Markdown 和代码高亮的实现；进入概览后，还要等待多类目录完成读取。

实时输出则有另一种成本。每个观看者每隔约 300ms 读取一次数据库，观看者增加时，相同任务的数据会被反复查询。

第十六步先记录基线，再分别处理启动、目录读取和实时快照，没有增加新的基础设施。

## 用同一份数据观察变化

验收环境准备了 242 个 Agent、160 个工具、60 个 Skill 和一条受控任务。两个已发布 Agent 放在候选目录末页，避免性能改动只在第一页正常。

任务还带有较大的附加上下文，Run 中保存了一段较长正文。这样才能检验实时接口是否无意中读取了与当前预览无关的数据。

优化前，生产入口 JavaScript 为 547177 字节。大目录下刷新概览会发出 17 个 API 请求。30 个观看者、10 轮快照读取执行了 1800 条 SQL。

这些数字分别描述下载、请求和数据库读取成本，后续对比也保持相同口径。

## 把页面代码放到需要它的时候

登录、概览、任务和编辑器的使用时机不同，因此把主要页面改成异步加载。概览里的运行详情组件也单独拆出，避免它间接把 Markdown 和高亮库带回首屏。

没有删减高亮语言，也没有改变 Markdown 的清洗、代码复制和宽表格滚动规则。加载过程中有明确状态；分包加载失败时，页面提供刷新入口。验收中实际拒绝了一次分包请求，确认不会出现空白页，刷新后可以恢复。

最终入口缩小到 91487 字节，降低约 83%。概览只需要入口和工作区分包，共约 108KB；最大单块约 301KB，构建不再出现超过 500KB 的提示。全部 JavaScript 总量因拆分辅助代码略增，用户在进入相应页面时再下载对应能力。

## 目录按页面读取，仍然保证候选完整

概览统计和最近任务已经由概览接口提供，没有必要提前下载全部工具、Skill 和授权目录。普通列表也有自己的分页接口。

现在，新建任务需要 Agent 候选，协作配置需要已发布 Agent，基本配置才需要模型、工具和授权目录。概览刷新因此从 17 个 API 请求降为 3 个：认证配置、当前身份和概览。

按需读取也引入了时序问题。表单不能先把“目录还没到”当成“没有可用候选”；切换页面或租户后，旧请求也不能覆盖新页面。因此必要目录到齐前先显示加载状态，路由或身份失效时取消读取并清理数据，迟到的响应通过读取版本丢弃。

末页候选仍然需要读全。浏览器实际检查了目录末页的 Agent，以及最后一页的工具和 Skill。优化减少了不必要的读取，没有让授权选项悄悄缺失。

## 让多个观看者共用一次短时读取

实时快照先改为字段投影。任务只取状态、租约和计数，最新轮次合入查询；Run 只读取实时预览字段，不反复取回完整输入和正式正文。

随后，在单个 API 实例内合并相同任务的并发读取。缓存键包含数据库、租户、任务和运行详情查看能力，非终态结果最多复用 250ms。初次连接直接读数据库，终态与异常不缓存；条目数量和单条大小都有上限。

一个观看者断开，不会取消其他人正在等待的共同读取。应用关闭时会取消剩余工作并清空状态。没有另外启动后台轮询器，也没有引入 Redis。

权限继续按原节奏重新查询。每次访问检查任务读取能力，运行详情权限改变后使用不同键。已有账号的身份解析也移除了重复的冲突插入与提交，用户、成员和角色仍从数据库新鲜读取。

## 分开记录局部基准与真实 HTTP 验证

同一份记录、同样 30 个观看者和 10 轮读取，字段投影先把 SQL 从 1800 条降到 1500 条；共享快照进一步降到 50 条。读取中位耗时从约 58ms 降到约 13ms，P95 从约 76ms 降到约 18ms。

这组微基准只统计快照及事务 SQL，没有计入 HTTP 鉴权。另一组验证使用真实密码会话连接 30 个 SSE 观看者，连续写入 8 次合成更新，确认每个观看者都收到最终内容。首帧中位约 94ms、P95 约 105ms。

它们都是本机受控结果。不同任务、多个 API 实例、生产网络和更长历史会话仍会产生不同成本，不能据此推算生产容量。

## 优化之后继续核对用户操作

本轮完整后端有 218 项测试通过、没有跳过；前端 91 项功能、6 项 UI 规则、类型检查和生产构建通过。缓存隔离、撤权、取消、错误恢复和原有文件能力都保留回归。

浏览器验证了分包失败刷新、大目录、实时输出断网恢复，并在三种状态下覆盖六种规定视口，共保留十八组截图与几何。合成任务完成后，草稿被正式结果替换，代码复制内容正确，Markdown 下载与原文逐字节一致；最终还巡检了 34 个页面。

这一步让登录和概览更轻，也降低了多人观看同一任务的重复读取。下一轮性能工作可以继续针对虚拟列表、超长会话和生产负载展开，并沿用这次明确区分下载、请求、SQL 与端到端验证的记录方式。
