# Begin Agent 建设实践之五 运行记录与详情的设计与实现

任务页能够解释一次对话内部的执行过程，运行列表则承担另一种工作：从许多次执行中找到需要排查的那一次。只有 Run 编码和状态时，用户还要反复打开任务，才能确认执行目标、使用的 Agent 和资源消耗。

Begin Agent 第五阶段补齐了运行记录与详情。列表增加任务与 Agent 名称、轮次、耗时和用量，筛选落实到服务端；详情支持步骤过滤、父子链跳转和执行中的自动更新。

## 用执行摘要帮助定位运行

任务、Run 和模型调用分别表示不同层级的活动。一个任务可以有多轮 Run，Run 又可能产生子运行和多次模型调用，因此列表需要同时说明任务归属与执行层级。

本次摘要保留任务编码、固定版本、父运行和根运行关系，并展示任务名、Agent 名称与轮次。耗时从 Run 创建计算到结束，执行中则计算到当前时刻。这个数值反映 Run 的经历时间，不能直接视为模型推理耗时。

Token 按实际模型步骤中的用量汇总，缺失调用单独计数。用户可以同时看到已知小计和缺失情况，避免把“没有上报”误读为“没有消耗”。列表只返回这些摘要，原始模型与工具输入输出继续放在详情中，减少列表响应内容。

## 让筛选覆盖完整记录

运行列表新增按任务编码、Agent、日期和根运行筛选，并支持搜索任务名、Agent 名称或运行编码。筛选条件随请求进入服务端，再执行分页，当前页之外的匹配结果也能被找到。

日期范围按北京时间计算，根运行筛选根据父运行关系判断。分页排序使用创建时间与编码，避免相同时间的记录缺少稳定顺序。更换筛选时回到第一页，防止旧页码让新结果看起来为空。

名称搜索还涉及权限。账号即使能读取运行记录，也未必能读取任务目录或 Agent 目录。本次分别检查这两类读取权限：没有任务读取权限时不返回任务名称，也不能通过标题查询判断某个名称是否存在；Agent 名称采用相同约束。

## 让详情跟随执行状态更新

运行详情新增步骤类型与状态筛选，用户可以只看模型调用，或集中查看失败步骤。父运行和根运行入口用于沿调用关系返回上层，固定版本编码则保留执行时的配置依据。

执行中的 Run 每约 1.8 秒更新一次，结束后停止轮询，离开页面也停止后续更新。请求失败时保留明确提示，允许手工刷新恢复；请求序号保护当前页面，较早响应无法覆盖新查询。

## 用浏览器发现布局边界

新增筛选项后，768px 视口暴露出按钮被挤出可见区域的问题。筛选栏改为按宽度换行，控件继续使用统一的 40px 高度和 8px 圆角。

低高度检查又发现额外 17px 的页面溢出。来源是屏幕阅读器使用的隐藏标签：绝对定位缺少局部参照，标签越过了内部滚动区域。将定位约束在各自标签容器后，页面恢复正常，无需缩小控件或隐藏筛选项。

本阶段后端相关回归 16 项、前端功能 39 项及 UI 规则 6 项通过。浏览器完成组合筛选、步骤查看和一次 503 故障恢复，并保留三种状态、六种视口共 18 组记录。运行数据使用隔离模拟模型，故障恢复采用浏览器注入的错误响应。

运行工作区现在能够从列表定位执行，再进入详情沿步骤与调用关系排查。下一阶段继续完善任务重新执行、快捷键发送和文本产物交付，让用户在查看结果之后完成后续操作。

具体接口、代码位置和证据见[第五步交付文档](../05-run-workspace.md)。
