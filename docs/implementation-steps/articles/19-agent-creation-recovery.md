# 创建已经成功，页面却说失败：如何安全地再试一次

第十八步解决了多人编辑覆盖的问题，第十九步遇到的是更早的一个时间点：用户点击创建，数据库已经写入 Agent，但响应在返回途中丢失。页面没有拿到编码，只知道请求失败。再点一次，如果系统把它当作新操作，就会出现两个同名 Agent。

网络失败不能告诉我们数据库发生了什么。请求可能没到服务器，也可能已经提交，甚至只是提交后的审计处理失败。仅仅禁用按钮能减少连点，却无法处理刷新、重启和响应丢失。系统需要记住“这是同一次创建”。

## 在请求之前给操作一个身份

这次改动让向导在首次请求之前生成一个 UUID。每次重试带上同一个 Idempotency-Key，服务端在当前账号和当前租户内识别这个操作。

服务器保存首次请求的基本信息摘要及创建结果。相同键与相同内容返回原来的编码；相同键却换了创建内容，则返回 409，让页面先核对原结果。创建 Agent 和保存回执放在同一个数据库事务里，避免出现“Agent 存在，但回执没有保存”的半成品。相同键的并发请求在事务内串行核对，数据库唯一约束再守住边界。

首次创建返回 201，再次确认返回 200，并通过响应头和审计标记说明这是重放。旧客户端仍可以不传键，但那样不能获得这份去重保证。去重也不靠名称：两个独立操作可以合法地创建同名 Agent。

## 找回结果，还要保住别人的编辑

创建回执保存了首次配置条件。假设创建成功后，另一位编辑者已经修改了名称，原页面随后恢复并保存，就必须看到冲突。若重放顺手返回最新条件，旧页面反而会被允许覆盖新修改。

因此，回执返回原始结果和初始 ETag。真正保存配置时继续比较 If-Match；条件过期返回 412，页面保留本地输入，等用户确认重新加载。这让第十九步的恢复与第十八步的并发保护接在一起，没有用恢复流程绕过条件检查。

同页恢复也区分两件事：原创建请求始终保持最初的名称、类型和状态；拿回 Agent 编码以后，再保存用户当前正在编辑的配置。因此用户在失败后改了名字，也不会因为重放被悄悄改回旧名。

## 刷新后的默认表单不能自动提交

刷新会丢失尚未保存的提示词和资源选择。若页面拿回编码后直接保存刚初始化的表单，就可能用默认值替换正确配置。

现在刷新后展示独立恢复面板，可以查询结果或重试原创建请求。成功后进入这个 Agent 的配置页，由用户核对保存情况；流程不会自动提交默认草稿。查询返回 404 时也不会换一个新键，因为“现在没查到”仍可能与一个正在处理的请求同时发生。

浏览器只在当前标签页保存原创建名称、类型、状态和请求标识，并按账号与租户区分。没有把提示词、模型密钥或整个编辑器复制进存储。存储不可用时，页面明确提示用户留在当前页确认，仍用内存中的原键重试。关闭标签页、清除或损坏记录后，自动恢复有边界，需要先核对 Agent 列表。

## 用真实故障验证恢复

验收时，让 Chromium 接收服务器已提交的响应，再故意丢弃它。第二次保存返回同一个编码，数据库只有一条对应创建，当前提示词也保存成功。另一个场景在丢响应后重启 API、刷新标签页，查询找回原 Agent，确认没有产生默认草稿写入。

还验证了请求根本未送达时的 404 与原键重试、另一编辑者修改后的 412、切换租户和账号后的隔离，以及浏览器存储写入失败。六类状态覆盖六种尺寸，修正恢复按钮间距后重新构建复验。完整后端 246 项、前端功能 121 项、UI 规则 6 项通过，另巡检 34 个页面。

这次新增了一张不可变回执表。实际本地库先备份再迁移，既有 24 张表的数据哈希与凭据主密钥保持一致。业务故障实验只在隔离库进行，没有调用模型供应商或 MCP。

创建幂等保证的是原请求身份仍然可用时，重试能找回同一个结果。它没有把所有网络操作变成恰好执行一次，也没有保存未提交的完整草稿。把这些保证的范围说清楚，用户才能知道何时可以安全重试，何时需要先核对已有结果。
