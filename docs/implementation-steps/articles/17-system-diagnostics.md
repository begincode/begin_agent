# 让“系统状态”能解释故障：Begin Agent 第十七步实践

任务一直在等，是 Worker 没运行、还没到重试时间，还是租约出了问题？如果状态页只有“就绪”和“未就绪”，这几种情况很难区分。

前十六步已经补齐任务、协作、权限、文件、真实模型联调和性能优化。本轮继续完善设计中的系统状态页，把排查需要的信息放到一个有权限边界、能刷新、能解释失败的入口。

## 先说清楚观察范围

API 和 Worker 是两个独立进程。API 能响应请求，并不能证明 Worker 正在消费任务。

Worker 原来会在持久数据目录写心跳文件，readiness 命令检查心跳时间和 PID。本轮保留这个机制，并补充主机信息，把记录分成就绪、过期或退出、损坏、其他主机、无法观察几类。

这里有一个部署边界：本机 PID 检查只能在相同主机和可见的进程环境中解释。共享目录里出现另一台机器的记录，不能用当前机器上的同号 PID 证明它还活着。因此页面写的是“已观测到就绪 Worker”，同时说明本机检查范围；不同主机或容器中的 Worker，应在自己的环境执行 readiness。

扫描也需要边界。一次最多读取 256 条记录，每个文件最多 16KiB；损坏 JSON、未来心跳、无效 PID 和非有限数值都不能撑坏整页。超过上限时，页面会明确提示统计不完整。

## 把“等待”拆成可解释的状态

PENDING 不一定意味着积压。

任务可能安排在稍后执行，也可能刚失败、正在等待下一次重试。如果直接用创建时间计算等待，正常退避就会变成告警。

本轮把待执行拆成“可领取”和“计划或重试等待”。可领取要求计划时间和重试时间都已到达；等待时长从两者中较晚的时间开始算。达到五分钟后，才进入长等待统计。

运行中的任务还要检查租约。租约已经过期，和压根没有租约，是两种不同问题；前者沿用 Worker 的重领规则，后者需要结合任务记录排查。页面提供任务详情入口，不在诊断过程中自动重试或修复。

异常列表最多十条，先展示租约问题，再展示长等待和最近一天失败记录。每条只带编码、标题、状态、原因和观察时间，诊断查询不读取提示词与结果正文。

## 系统权限不等于任务权限

管理租户设置的人，未必拥有任务查看权限。

所以状态接口先验证 tenant.manage，再单独验证 tasks.read。没有后者时，数据库、Worker 和运行方式仍可查看，队列部分明确提示需要权限，后端不会执行任务统计。所有队列查询都限定当前租户，并继续经过原有 RLS。

浏览器分别用管理员、仅有系统状态权限的账号和普通成员验证：受限账号看不到任务指标或按钮，普通成员无法直达状态页，管理员切换空租户后也不会带出原租户的任务。

## 失败时保留信息，也标记时间

刷新失败后直接清空页面，会丢掉排查线索；继续显示上次的绿色状态，又容易误导。

本轮保留旧样本，但同时显示读取错误和“当前状态尚未确认”，并保留采样时间。重试成功后再替换样本。初始加载与刷新中禁用按钮，离开页面、切换租户或权限变化时中止请求，过期响应不能覆盖新身份的数据。

数据库探测分别报告连接与迁移就绪、迁移不匹配和检查不可用。失败不会回显连接地址或底层异常。认证本身也依赖数据库，因此这页不承诺在全库断连时仍能登录查看诊断。

## 用故障验证入口

验收先启动真实隔离 Worker，确认空队列和心跳；随后停止它，构造六条合成任务，覆盖计划等待、重试等待、长等待、过期租约、缺失租约和失败记录。

浏览器还实际修改隔离迁移号，验证异常与恢复，并阻断一次读取，检查旧样本标记和重试。期间发现新任务入口多传了一个斜杠，点击后回到概览。修正导航参数、更新测试、重新编译重启后，再次实际点击进入详情，才完成这项验收。

最终后端 226 项测试全部通过；前端 98 项功能测试、6 项 UI 规则、类型检查和生产构建通过。四种状态覆盖六种规定视口，共 24 组截图与几何检查，34 个页面巡检通过。

本轮没有调用模型供应商或 MCP，业务写入都发生在隔离库。正式本地 API/Worker 已更新，原账号和业务数据保留。跨主机心跳、外部告警和生产容量仍需独立建设；当前页面提供的是有采样时间、权限约束和明确范围的诊断信息。
