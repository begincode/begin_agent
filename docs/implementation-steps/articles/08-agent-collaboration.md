# Begin Agent 建设实践之八 SubAgent 协作配置的设计与实现

主 Agent 能够调用子 Agent 之后，协作配置还需要支持日常调整：改变调用方式、设置单次超时、临时停用关系，再明确这些修改会影响哪些任务。若配置与历史执行混在一起，排查结果时就难以确定当时发生了什么。

Begin Agent 第八阶段补齐 SubAgent 关系编辑与启停，同时保留发布快照的边界。关系配置可以继续变化，已经提交的任务仍然能够解释自己的执行依据。

## 让关系配置可以持续维护

协作面板支持模型按需调用、预先串行和预先并行三种方式，并开放 1 到 1800 秒的单次超时。已有关系可以编辑、保存、取消或停用，停用后仍留在列表中，方便再次启用。

编辑时目标子 Agent 保持不变，修改只作用于关系设置。接口采用部分更新，未提交字段保留原值，避免只调整超时时意外重置调用方式或重新启用关系。

新增候选排除当前 Agent、已有关系、停用和未发布 Agent。候选目录也补齐分页，让较早创建的 Agent 不会因为落在第一页之外而无法选择。

## 重新启用也要检查循环

关系新增时检查循环还不够。例如 A 调用 B 的关系被停用后，B 可以新增对 A 的调用。如果随后直接恢复 A 对 B 的关系，就会出现环。

当前实现只把启用关系纳入有效图，但每次启用都会重新检查完整图。重复关系返回明确冲突，自调用直接拒绝，新增与启用也要求子 Agent 启用且已经发布。

关系图变更使用同一租户事务锁。两个并发请求分别增加不同边时，需要在前一个变更提交后再检查下一条边，防止两个请求各自看起来安全、合在一起却构成循环。删除也采用相同锁顺序，保持图操作一致。

## 区分当前关系与发布依赖

关系列表展示子 Agent 当前的名称、状态和发布版本，帮助配置者判断下一次发布将使用什么。历史任务的依据则保存在主版本的依赖快照中，两者承担不同职责。

修改模式、超时或停用关系后，需要重新发布主 Agent，才能进入新的依赖快照。原主版本与已经创建的任务不会随之变化。协作面板因此明确提示发布后生效，并提供前往基本配置发布的入口。

关系停用也不能被理解为立即撤销全部历史调用。需要立即阻止某个 Agent 执行时，应使用 Agent 自身的停用机制；资源授权撤销仍由原运行时检查处理。

## 用旧任务执行验证快照

浏览器先建立串行、19 秒的关系并发布主 Agent，再提交任务。随后把关系改为并行、31 秒并停用，重新发布得到不含子关系的新版本。

此时才处理此前提交的任务。真实队列与 Runtime 配合隔离合成模型产生两个父子 Run，任务仍使用原主版本和原子版本，执行依据仍是串行、19 秒配置。新版本没有子关系，原版本的关系参数也没有被改写。

这组顺序把配置变化与执行变化放在同一个场景中检查，比单独确认保存接口成功更能说明快照是否生效。

## 把权限和布局纳入验收

协作只读账号可以查看关系与子版本，没有新增、编辑或移除入口，写接口也会拒绝。浏览器还在子 Agent 之后新增了 60 个占位 Agent，确认跨页候选仍然可以选择。

本轮最终完整后端 161 项、前端功能 52 项、UI 规则 6 项通过。关系并发、循环、部分更新与固定版本都有回归覆盖；三种页面状态分别验收六种视口，共保留 18 组记录，并补充桌面与手机的目标卡片截图。

协作配置现在可以持续维护，发布时机与历史任务的边界也有执行证据。当前多编辑者仍采用最后提交字段生效的方式，关系修订号和超大目录的检索可以在后续阶段进一步补齐。
