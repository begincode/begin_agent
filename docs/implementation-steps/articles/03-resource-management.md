# Begin Agent 建设实践之三 工具与资源管理的设计与实现

资源数量较少时，工具管理看起来只是列表和编辑表单。随着工具、MCP 和 Skill 增多，列表分页、直接访问详情、Agent 绑定和运行时执行开始相互影响。工具被停用后能否继续执行，资源位于第二页时能否正常编辑，都会影响平台行为。

Begin Agent 第三阶段围绕这些问题补齐资源管理：增加工具启停与分组筛选，完善服务端分页和详情读取，并处理停用资源与 MCP 凭据变更带来的状态变化。

## 工具停用需要覆盖发布与执行

工具的启用状态进入创建和编辑流程，用户可以在管理页面停用资源。停用随后作用于两个关键位置：新版本发布时不能继续使用该工具，旧版本触发实际工具调用时也会检查当前可用性。

发布检查约束后续配置，执行检查则让撤销能够作用于已经发布的版本。若只在界面禁用选择框，历史版本仍可能保留工具绑定，并在执行时继续调用资源。

与此同时，历史版本和绑定记录保持原样。它们记录当时允许使用的能力，当前状态决定这次是否仍允许执行。两类信息分别保留，才能同时满足历史追溯与即时停用。

## 让停用资源仍然可以被移除

Agent 草稿可能已经绑定了后来停用的工具。如果资源停用后直接从编辑界面消失，用户反而无法清理这份草稿。

当前编辑页保留已有停用绑定的展示，允许取消选择；尚未绑定的停用项不可新选。用户可以看见配置中的问题并移除资源，发布后的历史版本也不会因此被改写。MCP 和 Skill 的绑定界面沿用相同处理思路。

浏览器验收实际完成了创建工具、绑定草稿、停用工具和移除绑定，并检查已发布版本编码保持不变。这组连续操作能检验状态之间是否衔接，仅分别检查编辑表单和发布接口还不足以覆盖它。

## 把资源详情从列表分页中独立出来

工具、MCP 和 Skill 列表增加服务端搜索、状态过滤和分页，工具进一步支持精确分组筛选。筛选在服务端执行，避免当前页之外的资源被遗漏。

详情页改为按实体编码直接请求接口。用户从链接打开某个资源时，不再依赖浏览器是否已经加载到它所在的列表页。接口仍然验证当前租户归属，跨租户编码返回 404，响应继续排除密钥与密文。

Agent 编辑页需要资源目录来还原已有绑定，因此工作台会分批补齐工具、MCP 和 Skill 元数据。如果分页结果重复、无法继续前进，加载过程会报错，防止出现无限请求。当前方案适用于现阶段的目录规模；资源进一步增长后，再评估搜索与缓存方式。

## 凭据变化后重新确认 MCP 能力

MCP 工具目录由检测获得，检测结果与当时的连接状态有关。修改或清除 Token 后，旧目录不能继续代表新凭据可访问的能力。

当前实现会清除旧工具发现结果及检测时间，要求重新检测。保存凭据与检测成功分别表达不同结果，页面和后端都需要保留这个区别。已有版本快照继续保留，不随当前检测结果变化。

本阶段使用本机隔离 MCP 服务验证协议与凭据轮换流程。这说明本地协议链路按预期工作，外部服务仍需结合其地址、凭据和网络条件单独验证。

## 用跨页与连续状态变化验证资源管理

本阶段相关后端测试 15 项通过，覆盖 61 条资源的分页、分组、详情租户隔离、停用发布限制和执行前撤销。前端完整检查中的 34 项功能测试、6 项 UI 规则测试，以及类型检查和生产构建通过。

浏览器在隔离数据库创建分页工具，检查第二页、分组查询和 Agent 目录。工具第二页、停用详情、移除停用绑定三种状态分别经过六种视口验收，共保留 18 组记录，新增数据没有进入实际业务库。

资源管理完成后，工具的当前状态能够沿着列表、草稿、发布和执行传递。第四阶段进一步把任务与运行汇总为运营统计，并提供查询操作记录的入口。
