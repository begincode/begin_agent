# Begin Agent 建设实践之二 Agent 版本对比与测试结果的设计与实现

Agent 的行为同时受到提示词、模型参数、工具和子 Agent 配置影响。一次修改之后，即使回答发生变化，也需要进一步确认变化来自哪里：运行使用了哪个版本，哪些配置不同，测试当时采用了什么期望结果。

Begin Agent 第二阶段把版本对比、固定用例和任务记录连接起来。用户可以选择两个已发布版本查看差异，也可以指定历史版本运行用例，再从最近结果进入对应任务。配置变化与执行证据因此能够相互对应。

## 对比配置时保留结构与语义

版本对比覆盖提示词、模型配置及快照、模型参数、执行边界、工具、Skill、MCP 和子 Agent。用户选择两个不可变版本后，页面按字段展示前后内容，并标出差异。

结构化配置需要处理一个细节：对象字段顺序不同，未必意味着配置改变。例如，模型参数中的两个键仅交换顺序，直接比较序列化文本就可能产生假差异。本次对比会稳定处理对象键顺序，让用户把注意力放在实际配置变化上。

比较过程保持已发布版本只读。历史版本用于说明某次执行当时的配置，后续编辑应发生在草稿中。若查看差异时改动了原版本，历史任务就难以继续解释。

## 让测试明确使用哪个版本

测试页增加了发布版本选择，发起执行时显式传递 `version_code`。用户可以用固定输入验证某个历史版本，也可以在调整配置后选择新版本再次运行。

这个操作把“希望测试的版本”落实为任务使用的版本。浏览器验收实际选择了较早的历史版本，随后检查生成任务的固定版本编码，两者一致；执行完成后，列表显示对应版本和断言结果。

测试仍然进入真实队列与 Runtime，复用实际任务执行路径。隔离验收只在模型响应处使用模拟实现，因此能够检查入队、执行、结果落库和页面展示之间的衔接，同时避免把这次结果扩大为真实供应商能力验证。

## 测试历史保留执行时的判断依据

固定用例允许编辑，但已经执行的任务需要保留当时的期望。假设某次测试要求输出包含一段文本，之后用户修改了用例，旧任务仍应按原期望解释自己的通过或失败。

本次实现保留任务执行时固定的版本与期望文本。修改用例后，历史任务的断言依据不会随之变化。相关后端测试专门验证了这一点，防止历史结果被当前配置重新解释。

用例列表新增 `latest_execution`，返回最近一次测试任务的编码、版本、状态、时间和断言结果。它提供快速入口，完整执行过程仍保存在任务与运行记录中。用户先看最近结果，再按需要进入任务查看详情。

## 控制结果展示的范围

用例列表中的最近执行摘要不返回模型正文或密钥。没有任务读取权限时，接口不提供测试任务信息，避免通过测试页面绕过任务权限。

版本对比中的提示词、工具和模型配置可能较长。页面让对比表格内部滚动，保留外层布局宽度；小屏用户仍可以按字段阅读，不必横向拖动整个页面。

当前固定用例采用“输出包含期望文本”的确定性断言，适合检查指定内容是否出现。开放问题的事实准确性、完整性和表达质量，需要后续引入更合适的评测方法，不能由一次文本包含断言代替。

## 验证版本与结果的一致性

本阶段相关后端测试 10 项通过，前端完整检查中的 33 项功能测试、6 项 UI 规则测试以及类型检查、生产构建通过。测试覆盖结构化差异、历史版本传递和用例编辑后的历史保留。

浏览器完成了选择历史版本、提交用例、等待实际执行、查看断言并确认固定版本的操作。版本对比和用例结果两种状态分别经过六种视口检查，共保留 12 组几何数据与截图。

到这里，一次测试可以沿着“用例、版本、任务、运行记录”逐层追溯。版本中绑定的工具和 MCP 还会继续发生启停与凭据变化，第三阶段进一步处理资源当前状态与历史配置之间的关系。
