# 让真实模型走完 MCP 工具链：一次可核验的联调

模型接口返回一句正确答案，能证明网络、密钥和基础协议可用。对于 Agent 平台，还需要确认模型真的选择了授权工具，工具真的执行过，子 Agent 的结果确实进入父任务，并且用户看到的实时内容与最终产物来自同一条执行链。

Begin Agent 的第十五步围绕这些问题展开。此前已有协议测试和合成模型验收；这一轮使用现有 DeepSeek、GLM 配置，通过独立 Worker 和本机独立 MCP 服务运行完整任务。用户确认外部业务 MCP 后补，因此这次结论只覆盖约定的本机服务范围。

## 把验收放到独立环境

真实联调需要凭据，但不需要污染正在使用的工作空间。

我们只读原有模型配置，在专用数据库中用独立主密钥重新加密，创建验收账号、MCP 连接和 Agent。API、Worker、MCP 各自独立运行，保留和实际部署相同的进程边界。模型只接收固定验收文字和算术数据，不发送业务资料、源码或 MCP Token。

任务关闭自动重试，并限制步骤、输出 Token、总预算和超时。这样，一次失败就对应一份可解释的执行记录，不会在后台悄悄反复调用供应商。

## 用不能预知的回执证明工具执行

MCP 验收服务只有一个工具：计算两个整数之和，同时返回一个随机 receipt。模型可以自己算出 184+207 等于 391，却无法提前猜中服务端回执。

任务先让串行子 Agent 完成预处理，再要求父 Agent 调用已授权的 MCP 工具。最终回复必须包含计算结果、服务端 receipt 和子运行标记。

核验时并不只读这句最终回复。还要检查实际子 Run 成功、不可变工具步骤成功、MCP 服务端事件中存在相同回执，以及任务生成了正式文本产物。缺少工具记录的任务，即使文字里写着“已调用 MCP”，也不能通过验收。

两条真实任务均完成了这条链路。DeepSeek 和 GLM 各产生三个模型请求：一次子 Agent 调用、一次父模型工具选择、一次工具结果回传后的最终回复。两个 MCP 动态回执分别与服务端记录、运行步骤和最终正文一致。

## 给真实调用留下可追溯的信息

接入真实服务后，只看到 MODEL_FAILED 或 TOOL_FAILED 往往不够。鉴权失败、限流、网络断开和协议错误需要不同的排查动作。

模型步骤现在保存供应商、型号、配置编码和供应商请求 ID。请求 ID 先经过格式与已知凭据检查，原始错误正文不入库；失败只保存安全错误分类、HTTP 状态与重试属性。

工具步骤也从授权别名改成了“服务名 · 工具名”，并保留源编码和别名用于追溯。用户在执行链里可以读懂正在调用什么，排查时仍能准确定位到具体连接和已发布版本。

联调中还发现，当前 MCP SDK 会把非成功 HTTP 状态转换成通用 JSON-RPC 错误。直接在最外层捕获异常，会丢掉 HTTP 401 和服务不可用之间的区别。修复选择在 HTTP 客户端边界保留数字状态及安全网络分类，再交给上层归因；不通过解析远程错误字符串猜原因，也不记录错误正文或认证头。

## 让检测失败之后的页面保持诚实

另一个问题出现在连接检测：某次工具发现成功后，下一次检测失败，旧的成功时间仍然保留。用户刷新页面，容易误以为服务仍然通过检测。

这一步在失败时保存安全错误码、撤销成功标记。旧工具目录可以继续展示作参考，但恢复检测之前不能发布新的 Agent 版本。页面同步刷新当前连接和资源目录，重新进入页面仍然显示失败原因。检测恢复成功后，错误清除，目录重新生效。

并发更改也需要约束。如果用户修改了地址或凭据，之前尚未返回的检测请求不能覆盖新配置。服务端在网络请求前后比较配置，避免旧结果错挂到新连接。

界面也明确区分两个结论：工具发现通过，表示 MCP 连接和目录有效；模型实际调用成功，则需要任务记录证明。

## 用真实浏览器核对用户看到的结果

浏览器从表单提交 DeepSeek 任务后，在任务仍为 RUNNING、正式 output 为空、产物数量为零时，已经显示了真实上游的思考内容。完成后，页面出现计算结果和服务端回执，执行链能看到子 Agent 与 MCP 工具；刷新后结果保持一致。

MCP 页面则经历了独立服务真实返回 HTTP 401、检测失败、刷新仍显示失败、恢复服务后检测成功的过程。运行详情展开后，可以看到与供应商记录对应的请求 ID。相关状态覆盖六种规定视口，保留十八组截图与几何数据，并补拍错误和请求 ID 的目标截图。

最终完整检查有 211 项后端测试通过、没有跳过，前端 83 项功能测试、6 项 UI 规则、类型检查和生产构建也通过。两个完整任务共上报 2281 Token；加上两次基础连通性检查，本轮八次真实请求共上报 2348 Token。这是供应商用量记录，不是费用账单。

本轮完成了真实模型和独立 MCP 服务之间的闭环，也留下了安全诊断和可复用的只读验收脚本。外部业务 MCP、MiniMax/Kimi 配置、目标 Linux 环境和生产负载仍需继续验证；后续接入有写入副作用的工具时，还要补上下游幂等保障。
