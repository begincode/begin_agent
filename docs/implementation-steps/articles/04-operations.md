# Begin Agent 建设实践之四 运营统计与审计查询的设计与实现

任务、版本和资源能够正常运行之后，管理者还需要了解近期使用情况：产生了多少任务，执行成功率如何，调用了哪些模型，以及某次配置操作由谁完成。

Begin Agent 第四阶段新增近期运营统计与审计筛选。实现重点在于明确时间、计数、用量和权限口径，让界面上的数字能够与具体任务及运行记录对应。

## 先说明统计数字代表什么

概览页提供最近 7 天和 30 天两种范围，按北京时间的日历日归集数据。任务按创建日期计入，并展示其当前状态；同一任务继续多轮对话，不会因此增加任务数。Run 和模型调用分别累计，反映不同层级的执行活动。

成功率采用成功任务数除以成功、失败和超时任务总数，取消任务不进入分母。平均运行耗时只统计已结束的 Run。任务当前状态后续可能改变，因此历史日期桶中的状态分布也可能变化，不能把它理解为当天结束时冻结的快照。

时间窗口采用起点包含、下一日边界排除的方式查询，避免午夜附近的数据重复计入或漏掉。页面补齐范围内的日期桶，没有任务的日期也能连续展示。本阶段后端验证包含时区与日期边界检查。

## 模型用量保留已知与未知的区别

模型调用次数基于实际的模型步骤，按对应不可变版本中的模型快照汇总。一个任务可能触发多次调用，子 Agent 也可能产生新的运行，因此任务数不能直接替代调用次数。

Token 只累计实际已上报的用量，同时单独标识未上报调用。部分调用缺失数据时，已知小计仍然可以展示，但不能被理解为全部消耗。负数、非有限数和不安全的大整数也不会进入正常统计。

当前概览提供任务、运行和模型使用计数。费用需要结合供应商价格、缓存规则及具体计费口径，本阶段没有据此估算金额，也没有引入计费或配额功能。

## 统计接口继续执行数据权限

汇总数据同样可能暴露业务信息。只有概览访问入口，并不意味着用户可以看见当前租户的全部任务和运行情况。

当前实现分别检查任务读取与运行读取权限。缺少相应权限时，对应统计与明细为空，后端也不查询受限数据。这样可以避免列表页隐藏了记录，概览卡片却仍泄露数量或用量。

## 让审计查询帮助定位具体操作

审计页面支持按操作者、日期与文本过滤，并采用每页 50 条的服务端分页。文本查询可以匹配路径、资源和姓名等信息，操作者目录则提供明确的筛选入口。

列表展示可读的操作名称，详情保留原始路径和状态。展示层帮助用户理解操作，原记录继续用于追溯。操作者名称取当前目录，历史记录中的操作者编码保持不变；用户名展示变化后，仍可沿编码确认身份关联。

快速切换筛选时，还需要处理响应顺序。较早的请求可能更晚返回，若直接覆盖页面，就会出现筛选条件已变而结果仍属于上一次查询的情况。本次增加请求顺序保护，只接受当前有效查询的结果，并在组件离开后停止写回。

## 结合数据口径与页面操作验收

本轮最终完整后端检查为 151 项通过，前端功能测试 36 项、UI 规则测试 6 项通过，类型检查、生产构建和代码检查也通过。其中包含时间边界、实际模型调用计数、Token、租户隔离和审计响应乱序保护。

浏览器实际切换到 30 天统计，确认返回 30 个日期桶，并检查审计第二页、操作者与日期过滤。三种状态分别完成六种视口验收，共保留 18 组记录。最终构建还通过了 31 个页面冒烟检查。

统计按请求聚合，当前尚无缓存；更大规模的数据需要进一步评估查询性能。本轮任务数据来自隔离模拟执行，验证范围包括计数、归集、权限和展示。实际服务已提供最新构建，API 与 Worker 保持运行，既有账号和模型数据保留。
