# Begin Agent 建设实践之九 成员目录与权限详情的设计与实现

成员管理需要回答两个不同的问题：一个账号是否属于当前租户，以及它现在能够访问哪些功能。账号、成员和角色都可能被停用，单独显示一个状态标签，很难解释真正的访问条件。

Begin Agent 第九阶段补齐成员目录与独立权限详情，让角色分配、实际权限和访问状态可以同时核对。

## 把角色分配与角色定义分开

原成员页面只有在管理员具备角色编辑权限时才读取自定义角色。仅负责成员管理的人因此看不到完整分配目录，即使服务端允许他授予某些角色，也无法从页面操作。

新增的成员角色目录只要求成员管理权限。它展示内置和自定义角色，并逐项判断是否可以授予：停用角色不可分配，超出操作者自身权限的角色不可授予，租户管理员身份也有单独限制。

界面提前禁用不允许的选项，保存接口仍负责最终校验。读取分配目录不会获得编辑角色定义的权限，委派者能够完成职责范围内的操作，也不能借此提升自己或其他人的权限。

## 用独立详情解释实际权限

成员详情使用不可变的成员编码，可以刷新和直接访问。页面同时展示账号状态、成员状态、角色状态与当前实际权限，避免把三者混成一个“启用”。

普通账号需要通过成员和角色检查；平台管理员则继续使用平台身份的访问优先级。详情会解释这一差别，防止把停用一条成员记录误认为撤销了平台管理身份。

角色选择区还会预览拟分配角色的权限。它与当前实际权限分别展示，用户可以先确认将要授予什么，再保存变更。成员页面不修改全局账号姓名，账号资料继续由平台用户管理维护。

## 让目录查询覆盖全部成员

列表搜索、角色筛选、成员状态筛选和分页都进入服务端，避免只在已加载的第一页查找。排序同时使用加入时间和成员编码，使时间相同的记录仍有稳定顺序。

当前读取范围继续服从租户与接口权限，任务操作仍检查创建者或任务管理权限。本阶段没有引入独立的成员数据行范围，也没有把原型中的“仅本人数据”显示成已经实现的能力。

## 用重新启动后的页面验证行为

本阶段相关后端 10 项、前端功能 56 项和 UI 规则 6 项通过。随后重新编译、启动 API/Worker，再由独立浏览器验证受限管理员分配观察者角色、详情刷新、第二页和组合筛选。

实际检查还发现，较长的英文姓名会撑宽手机详情内容区。修复标题换行后再次编译启动，并把内部内容宽度加入检查；三种状态各完成六种视口，共保留 18 组记录。

所有成员数据写入都在隔离库。实际服务单独验证就绪、最新构建和登录页，保留原有账号、密钥与业务数据。实现与验收证据见[第九步交付文档](../09-member-permissions.md)。
