# 两个编辑者同时保存时，系统该保住什么

一个编辑者修改 Agent 的名称，另一个编辑者修改提示词。两个人都打开着同一页，也都看见了保存按钮。后保存的人，应不应该把先保存的结果覆盖掉？

Begin Agent 原来已经给草稿加了 revision：提交旧修订号会被拒绝。但排查编辑器后发现，页面实际上分三次请求——先保存基本信息，再保存草稿，最后发布版本。草稿冲突时，名称可能已经被第一条请求改掉了。

第十八步从这里开始，补齐多人编辑保护。

## 一次保存应该有一个结果

用户点一次“保存草稿”，通常会认为名称、类型、状态和提示词一起保存。后台拆成几个请求，用户却未必知道其中哪一部分成功了。

本轮把已有 Agent 的元数据、草稿和可选发布放进同一个数据库事务。模型停用、授权变化或参数错误导致发布失败时，元数据和草稿一起回滚。成功后再统一提交，页面不会留下“名称更新了，提示词没更新”的中间状态。

这也约束了发布服务本身：它需要支持参与外层事务，不能在组合操作尚未完成时提前提交。

## 保存前，比较编辑者看到的状态

行锁能让两个请求排队，却不能证明排到后面的编辑者看过最新内容。

因此本轮增加配置快照和强 ETag。页面读取时拿到令牌，保存时通过 If-Match 带回来。服务器在事务锁内比较：状态一致才写入；缺少条件返回 428，状态变化返回 412。

配置令牌覆盖元数据、草稿修订和协作配置。关系集合另有自己的令牌；单独编辑关系不会因无关的父 Agent 提示词变化被拒绝。当前子 Agent 版本也进入比较，避免用户在旧页面上无意发布新的依赖快照。

这里的令牌是内容标识，不是权限，也不是全系统的修改次数。用户、租户和权限依然每次验证；同一可见状态也可以得到相同令牌。

## 拒绝覆盖之后，还要保住本地输入

如果冲突时直接刷新页面，服务器的新配置保住了，用户刚写的提示词却丢了。

新的冲突面板会保留本地输入，停止重复保存，并提供重新加载入口。用户还要明确确认放弃本地编辑，页面才读取并替换表单。取消确认不动输入；重新加载失败，同样保留原内容。

浏览器验收使用两个独立账号：A 先保存名称和提示词，B 提交旧页面中的长名称与长提示词。B 收到 412 后，本地字段仍在；服务器的两个字段都保持 A 的值。随后阻断一次重新加载，确认失败也不会清空表单，再恢复网络完成保存和发布。

验收还发现页面底部有第二个保存按钮。处理函数虽已拒绝冲突后的重复提交，按钮外观仍可点击。本轮补齐了它的禁用状态，再重新编译验证。

## 协作和发布也需要条件

协作关系的调用方式、超时和启停会进入下次发布快照，最后保存覆盖同样可能改变执行行为。

本轮验证 A 将关系改为并行执行、31 秒超时后，B 的旧 7 秒更新被拒绝；再制造过期删除，确认关系没有被移除。重新加载后，用户才可以继续删除或调整。

发布也有单独验证：另一会话先把关系改为 55 秒，旧页面的发布被拒绝，元数据、草稿和版本数量没有部分变化。重新加载后发布，新版本才采用最新的 55 秒配置。

原版本任务在编辑前通过真实队列与本机合成网关执行，留下两个父子 Run。编辑后比较原版本、运行、产物、轮次和输出，全部保持不变。合成网关测试没有访问供应商，不能把其中的测试 Token 当作真实调用用量。

## 新建成功之后，失败也要能恢复

向导还有一个容易忽略的阶段：Agent 已创建并返回编码，后续草稿保存却发生冲突。

创建接口现在同时返回初始配置条件，向导保留已经取得的编码。它不会通过临时获取最新条件来盲写，也不会在失败后再创建一个 Agent。

浏览器实际暂停首次保存，由另一账号抢先修改名称，再放行请求。过期条件被拒绝，本地提示词仍保留；确认丢弃后加载服务器新名称，并清除未保存配置。恢复保存成功，全流程只创建了一次。

这个保证以客户端已经拿到编码为前提。创建请求已提交但响应丢失时的幂等恢复，仍需要后续单独建设。

本轮最终后端 235 项测试全部通过，前端 106 项功能、6 项 UI 规则、类型检查与生产构建通过。六类状态完成 36 组视口截图和几何检查，34 个页面巡检通过；本地 API/Worker 已重新启动，并保留原账号和业务数据。

系统现在会拒绝过期页面的覆盖，并保留用户处理冲突所需的输入和选择。自动字段合并、跨页面本地草稿和跨服务事务仍未加入；这些能力需要各自明确的数据边界与验证。
