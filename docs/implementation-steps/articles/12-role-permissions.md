# Begin Agent 建设实践之十二 角色权限矩阵与成员联动的设计与实现

角色管理已经能够创建权限集合，但只把权限显示为一串文字，很难比较不同角色，也无法判断一次修改会影响多少成员。当角色数量超过默认读取上限时，前端搜索还可能遗漏没有加载的记录。

第十二阶段补齐服务端角色目录、权限矩阵和成员统计，并把角色变更与实际访问状态一起验证。

## 让目录完整，让权限容易比较

角色目录把内置角色和自定义角色放进同一套分页规则。搜索名称或编码、筛选状态都先在服务端执行，再返回当前页，避免在截断的数据上搜索。

矩阵以角色为行、具体权限为列，逐项显示是否授予。它负责比较和查看，编辑则进入单个角色的分组表单，分别配置任务、Agent、资源和组织管理权限。

较宽的矩阵在容器内部横向滚动。手机仍可以读取角色和成员信息，再向右查看权限，整页不被表格撑宽。

## 统计数字需要明确口径

矩阵同时展示成员总数和启用账号成员数。前者包括停用成员，后者要求账号、成员记录都启用，但仍不能直接称为“可登录人数”。角色停用、租户停用和平台管理身份，还会影响实际访问。

这些数字也需要权限边界。没有成员管理权限时，接口返回空值，页面显示“—”，而不是显示一个假零或通过角色页面泄露成员统计。

验证准备了三条使用同一角色的成员记录：一条正常、一条成员停用、一条账号停用。结果应为总数三、启用账号成员一，既检验聚合逻辑，也让口径可以解释。

## 不能通过编辑间接绕过权限边界

保存请求中的权限不能超出操作者自身权限，这只是第一道检查。假设一个受限角色管理员找到高权限角色，把它的权限全部清空，请求体虽然没有新增高权限，却仍然修改了不属于其管理范围的角色。

本阶段同时检查目标角色已有权限。超出操作者范围的角色在矩阵里只读，服务端拒绝覆写，避免用较低权限的请求间接影响高权限角色。内置角色继续只读。

本人角色变更也有相应处理：不能停用当前使用的角色；撤销自己的角色管理权限后，重新读取身份并离开该页面，导航和接口都按新权限生效。

## 用成员实际访问验证角色设置

浏览器先创建观察者角色，再增加 Agent 读取权限，确认成员详情出现对应权限；随后停用角色，成员详情变为角色失效且权限为空；恢复后重新得到正确权限。

这些操作影响后续鉴权，不改写已经发布的 Agent 版本和历史执行记录。矩阵展示的是当前配置，历史记录仍保留原来的版本语义。

补查平台账号降权时，还验证了一个容易忽略的场景：平台管理员选中自己不是成员的租户后自行降权。页面必须重新解析自己的成员租户，并清除此前工作区数据，才能避免继续停留在失效的租户选择上。

## 修复后重新编译，再测量

本轮完整后端一百七十三项、前端功能六十八项和 UI 规则六项通过。浏览器发现横屏时隐藏的表格标题多撑出约三像素外层滚动，定位到 caption 的绝对定位后修复，再次编译、启动和复验。

第十二步三种状态共十八组规定视口通过；第十一步的十八组也在最终构建上重验。最终三十四个页面巡检没有脚本异常，业务写入都在隔离库，实际服务保留原账号与模型数据。

实现、统计口径与验收证据见[第十二步交付文档](../12-role-permissions.md)。
