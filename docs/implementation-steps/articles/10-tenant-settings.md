# Begin Agent 建设实践之十 当前租户设置的设计与实现

租户设置里的一次改名，看起来只是更新一个输入框，实际涉及三个问题：正在修改哪个租户、操作者可以修改什么，以及更新后其他页面是否仍显示旧名称。

第十阶段把当前租户设置做成独立工作区，让租户信息、权限边界和停用后的行为可以在同一个页面核对。

## 把当前租户作为操作范围

普通租户管理者不需要浏览全平台租户，也不应该通过提交一个编码修改其他组织。本阶段新增当前租户读取和改名接口，目标直接来自鉴权上下文，只接收租户名称。

服务端拒绝状态、目标编码等额外字段；界面则把租户编码显示为只读。即使修改浏览器请求，也不能通过当前租户改名接口绕过平台管理权限。

平台管理员继续使用既有平台接口创建租户及调整状态。两种职责在同一个工作区呈现，但服务端按各自的权限边界执行，避免把租户管理权限扩大为平台管理权限。

## 让概况数字服从实际权限

有权修改租户名称，并不意味着有权查看成员和资源情况。因此，概况接口按权限分别提供成员、Agent 与资源统计。

缺少权限时返回空值，页面显示“—”和原因。这里不能显示零，因为零表示租户确实没有数据，而空值表示当前账号无权读取。区分这两种情况，才能避免错误的运营判断。

统计口径也保持明确：启用租户管理员数量按启用账号和启用管理员成员记录计算；已有发布版本的 Agent 数量不等同于当前启用数量。

## 保存后同步整个工作空间

改名成功后，页面重新读取当前身份与租户目录，再刷新工作空间数据。输入框、详情标题和顶栏租户选择器因此保持一致，刷新页面也不会退回旧名称。

创建租户沿用相同的同步过程。已经选中的租户保持不变；尚未加入任何租户的平台管理员创建首个租户后，会同步获得当前选择，页面可以直接读取新租户信息。

## 用停用与恢复检验权限边界

停用租户后，历史配置仍然可读，普通管理者的名称输入和保存按钮禁用，服务端也拒绝直接写请求。平台管理员可以通过平台接口恢复启用。

浏览器验收覆盖了完整过程：创建租户，使用只有租户管理权限的账号改名，刷新核对顶栏，平台停用，普通账号读取历史并确认写入返回 403，最后恢复启用。全过程同时核对另一租户的信息没有变化。

验证脚本曾在租户切换尚未结束时跳转，导致切换完成后回到概览。补上完成等待，并给独立验收请求补齐当前租户标识后，流程重新通过。明确测试所处的租户上下文，同样是多租户验收的一部分。

## 每一步都在重启后的应用上检查

本阶段完整后端 167 项、前端功能 59 项和 UI 规则 6 项通过，类型检查和生产编译通过。重新启动 API、Worker 与隔离验收实例后，三种租户状态分别覆盖六种规定视口，共保留 18 组记录，并核对长英文名称的换行与内容区宽度。

本轮没有数据库结构迁移，业务操作只写隔离库。实际服务保留原有账号、模型配置和密钥，继续使用独立账号体系。代码范围、接口和证据见[第十步交付文档](../10-tenant-settings.md)。
