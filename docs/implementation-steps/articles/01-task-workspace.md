# Begin Agent 建设实践之一 任务执行工作区的设计与实现

用户提交任务后，需要知道 Agent 是否仍在执行、执行到了哪一步，以及失败发生在哪里。任务可能包含多轮对话、子 Agent 和工具调用，仅靠一条最终回复，很难解释整个过程。

Begin Agent 第一阶段补齐了任务执行工作区：在对话旁展示运行链路，把实际记录的轮次、步骤、耗时与 Token 用量组织起来，同时增加“我的任务”筛选。用户可以继续阅读对话，也可以展开执行记录定位问题。

## 用任务与运行组织执行过程

任务代表用户持续推进的一件事，Run 表示其中一次执行。同一个任务可以有多轮执行，一次执行也可能派生子 Agent。页面需要保留这些关系，才能解释哪一次运行属于哪一轮，以及子运行由谁发起。

本次新增任务执行摘要接口 `GET /api/v1/tasks/{task_code}/execution`，从当前任务的真实运行记录生成展示数据。摘要保留轮次、父子关系、名称、状态、耗时和步骤信息，前端据此排列运行链路。用户无需逐条打开运行详情，就能先判断执行停留的位置，再进入完整记录排查。

摘要的边界也很明确：它服务于快速理解执行过程。原始消息、完整上下文和工具输入不进入这份响应，减少信息拥挤，也避免在任务侧栏暴露不必要的数据。

## 让进度与用量对应实际记录

Agent 执行过程中，后续步骤可能由模型临时决定。一个工具返回结果后，模型可能继续回答，也可能再调用工具。在无法确定总步骤数时，百分比进度很难准确表达剩余工作。

当前页面展示状态、已记录步骤数和最近步骤，用户据此了解实际发生的动作。步骤数量只代表已经落库的记录，不能换算为任务完成比例。耗时采用 Run 的时间信息，用量则读取模型实际返回并记录的 Token。

未返回用量时，界面显示“—”或“未返回”。零表示有明确记录且数值为零，缺失表示当前无法得知，两者会影响用户对资源消耗的判断，必须保持区别。

## 为执行链安排合适的阅读空间

桌面任务页把执行链放在对话右侧，支持展开和收起，并在本地保存用户偏好。对话和执行记录同时可见，适合观察较长任务，也方便对照回复与工具步骤。

当页面宽度不超过 1000px 时，右侧栏自动隐藏，用户通过“运行链路”页签查看相同内容。窄屏下让链路获得独立空间，可以保留底部输入区，避免对话、侧栏和输入框互相挤压。

执行期间沿用约 1.8 秒的轮询更新。离开任务页面后停止更新，执行摘要的加载错误单独提示，已有对话仍然可以阅读。这种安排让执行监控与内容阅读保持各自可用；当前任务链路的状态更新仍属于短轮询，不提供逐 Token 的流式展示。

## 把归属筛选与权限放在服务端

任务列表增加了“全部任务”和“我的任务”两种范围。选择“我的任务”时，前端提交 `mine=true`，服务端按当前用户的创建者身份过滤，切换范围后重置分页。这样翻到下一页时，查询范围仍然一致。

执行摘要同时要求任务读取和运行读取权限，并先确认任务属于当前租户。拥有任务阅读权限，并不意味着可以读取全部运行细节。接口将这两类权限分别落实，跨租户任务也无法通过编码直接访问。

## 用真实交互检验工作区

本阶段相关后端测试 9 项通过，前端完整检查中的 31 项功能测试和 6 项 UI 规则测试通过，类型检查与生产构建也通过。验证覆盖归属筛选、运行用量、跨租户访问和运行权限约束。

浏览器验收实际操作了执行链展开与收起、“我的任务”筛选，并对三种页面状态各检查六种视口，保留了 18 组截图与几何记录。检查重点包括控件尺寸、页面溢出和输入区可见性。运行数据来自隔离环境中的模拟模型执行记录，这些结果验证了任务展示链路。

这一步建立了任务与执行记录之间的对应关系。用户看完一次运行后，还需要知道它使用了哪份 Agent 配置，以及修改配置后结果是否符合预期。第二阶段沿着这个问题补齐版本对比和测试结果追踪。
