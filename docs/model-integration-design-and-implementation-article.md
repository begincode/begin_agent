# 企业级 Agent 平台建设：模型对接的设计与实现

接入第一家模型时，最直接的实现通常是拼好地址、带上 API Key，再把返回内容显示到页面。随着第二家、第三家供应商接入，问题开始集中出现：同名参数的取值不同，思考模式的开关不同，流式结束帧不同，工具参数还可能分成几十段返回。

这些差异最终会影响平台行为：用户选择的思考级别是否真正进入请求？页面显示“完成”时，上游是否正常结束？模型配置保存成功后，究竟验证过哪些能力？

本文以 Begin Agent 的实际代码为例，说明 DeepSeek、GLM、MiniMax、Kimi 四家模型的接入设计，以及配置管理、协议适配、流式处理和验证方法。实现采用 FastAPI、Pydantic、SQLAlchemy、PostgreSQL、httpx 和 Vue 3。

**本文对应 2026 年 10 月 23 日的实现与验证快照。** DeepSeek、GLM 已完成指定型号的真实 API 验证；MiniMax、Kimi 已完成适配代码和模拟协议测试，真实调用仍待可用配置验证。文中的能力范围以当前代码覆盖的型号为准。

## 一、先确定模型接入层的边界

Agent 执行任务时，上层更关心“输入哪些消息、允许哪些工具、如何取得结果”。供应商使用哪个地址、如何传思考参数、如何解释业务错误，可以收敛到模型接入层。

当前实现分为五部分：

| 部分 | 主要职责 | 代码位置 |
|---|---|---|
| 配置服务 | 模型配置增改、启停、密钥加解密、调用配置读取 | `app/services/model_profiles.py` |
| 统一契约 | 消息、生成参数、工具调用、响应和流式事件 | `app/model_gateway/domain/chat.py` |
| 模型网关 | 按供应商选择适配器，提供统一调用入口 | `app/model_gateway/gateway.py` |
| 供应商适配器 | 参数转换、型号限制、供应商错误码 | `app/model_gateway/adapters/` |
| 公共传输内核 | HTTP、SSE、增量组装、用量与结束校验 | `app/model_gateway/adapters/openai_compatible.py` |

完整调用过程如下：

```text
模型配置页面
  → 配置 API → 密钥加密 → PostgreSQL

对话页面提交 profile_code 和消息
  → 对话 API
  → 从数据库读取已启用配置，解密凭据
  → 结束数据库读事务
  → ModelGateway 选择供应商适配器
  → 构造请求并调用官方 HTTPS API
  → 解析为统一响应或事件
  → 页面展示正文、思考信息和用量
```

数据库事务在外部调用前结束，是这里一个容易忽略的细节。模型生成可能持续很久，配置查询完成后就可以释放数据库连接，避免一次长时间生成一直占用连接池。

这套结构也为后续 Agent Loop 留出接口：任务执行器调用网关即可，供应商协议留在适配层内处理。当前项目已经具备模型调用和工具调用协议能力，完整的 Agent Loop、业务工具执行器仍需继续建设。

## 二、模型配置入库，密钥留在服务端

模型配置需要跟随产品操作变化。用户在页面新增配置、修改密钥或停用模型后，后续调用应读取最新配置，因此当前实现把配置存入 PostgreSQL 的 `model_profile` 表。

表中的核心字段包括：

| 字段 | 用途 |
|---|---|
| `profile_code` | 不可变的配置标识，供对话接口引用 |
| `provider_code` | 选择 DeepSeek、GLM、MiniMax 或 Kimi 适配器 |
| `display_name` | 页面显示名称 |
| `model_code` | 上游实际使用的模型型号 |
| `base_url` | 对应供应商和套餐的 API 基础地址 |
| `api_key_ciphertext` | API Key 密文 |
| `enabled` | 是否允许继续调用 |

同一家供应商可以保存多份配置，例如不同型号或不同套餐端点。`profile_code` 标识具体配置，`provider_code` 标识协议实现，两者承担不同职责。

配置新增时，服务端使用 Fernet 加密 API Key，再将密文写入数据库。加密主密钥独立保管；本地开发环境使用受限权限的持久文件，也支持外部提供主密钥。主密钥需要与数据库备份分开保管，丢失后无法解密已有凭据。

配置列表和保存响应都不返回密钥。编辑时，前端省略 `api_key` 字段表示保留原密钥，提交新值才进行替换。凭据也不会进入普通对话请求：前端只提交 `profile_code`，由服务端读取配置并解密。

地址本身同样需要约束。当前实现校验供应商官方 HTTPS 域名和已知基础路径，禁止跟随重定向，避免把携带凭据的请求转发到未知主机。参数校验错误和上游异常响应也经过处理，避免回显密钥或完整请求内容。

这些措施解决了当前接入链路的凭据存取问题。企业公开部署还需要补齐租户归属、配置使用权限、密钥轮换和审计；当前本机管理保护尚未覆盖这些能力。

## 三、统一请求表达调用意图，适配器落实具体协议

对话接口使用一份内部请求模型，核心定义如下，省略了部分长度与数值约束：

```python
class ChatCompletionRequest(BaseModel):
    model_config = ConfigDict(extra="forbid")
    profile_code: str
    messages: list[ChatMessage]
    temperature: float | None = None
    max_tokens: int | None = None
    thinking: Literal["auto", "enabled", "disabled"] = "auto"
    reasoning_effort: Literal["low", "medium", "high", "xhigh", "max"] | None = None
    tools: list[ToolDefinition] = Field(default_factory=list)
    tool_choice: Literal["auto", "none", "required"] = "auto"
```

内部契约容纳四家接入所需的参数集合，具体型号再校验自己支持的组合。例如，内部允许 `medium`，并不代表每一个模型都接受这个级别。

页面发起一次流式请求可以使用以下形式，其中配置标识由保存配置时取得：

```http
POST /api/v1/chat/stream
Content-Type: application/json
```

```json
{
  "profile_code": "替换为已保存的配置标识",
  "messages": [
    {"role": "user", "content": "解释一下数据库连接池的作用"}
  ],
  "thinking": "enabled",
  "reasoning_effort": "high",
  "max_tokens": 4096
}
```

非流式使用 `/api/v1/chat`，返回完整 JSON；流式使用 `/api/v1/chat/stream`，返回 SSE。客户端通过接口选择输出方式，服务端再生成供应商所需的 `stream` 参数。

网关维护供应商与适配器的显式映射：

```python
ADAPTERS = {
    ProviderCode.DEEPSEEK: DeepSeekAdapter,
    ProviderCode.GLM: GLMAdapter,
    ProviderCode.MINIMAX: MiniMaxAdapter,
    ProviderCode.KIMI: KimiAdapter,
}
```

四个适配器复用公共 HTTP/SSE 实现，各自负责 `build_payload` 和错误策略。新增协议差异时，可以在对应适配器和测试中定位，不必把所有分支堆进路由函数。

## 四、四家适配的工作，落在具体参数和响应语义上

当前代码处理的主要差异如下。这张表描述项目已经实现的策略，不代表供应商全部型号的能力。

| 供应商 | 当前实现的关键处理 |
|---|---|
| DeepSeek | 显式发送思考开关；思考模式校验 `low/high/max`；拒绝思考模式下的温度配置及 `required` 工具选择；流式请求用量 |
| GLM | 校验温度范围与精度；指定 Flash 型号不能关闭思考；设置历史推理保留；流式工具请求使用 `tool_stream`；处理业务错误码和异常结束原因 |
| MiniMax | 使用 adaptive thinking 和 `reasoning_split`；按型号限制思考开关、强度；转换输出长度字段；检查 `base_resp`；处理最终完整消息帧 |
| Kimi | 区分 K3、K2.7 Code、K2.6；按型号校验推理强度、思考开关和工具选择；处理固定温度；转换输出长度字段 |

以输出长度为例，内部统一使用 `max_tokens`，MiniMax、Kimi 适配器将其转换为对应请求字段：

```python
if request.max_tokens is not None:
    payload["max_completion_tokens"] = payload.pop("max_tokens")
```

思考参数的差异更大。当前 Kimi 实现对 K3 和 K2.x 分别处理：K3 不携带 K2 专用的 `thinking` 对象，K2.x 则根据型号组织思考参数，并拒绝当前未支持的 `reasoning_effort`。

GLM 还涉及套餐端点。此次真实验证使用 Coding Plan 专用路径 `/api/coding/paas/v4`。模型名称、密钥权限和套餐端点需要匹配，平台应把这些信息作为一份具体配置管理。

遇到不支持的组合，适配器在调用前直接返回清晰错误。例如用户给不支持温度调整的模型设置温度，继续发送或静默丢弃都会让用户难以判断配置是否生效。当前实现选择显式拒绝，并提示可以使用的参数。

## 五、能力信息同时约束页面与后端

有了型号差异，前端控件也需要随模型变化。配置列表响应会附带 `GenerationCapabilities`，包括可用思考模式、推理强度、流式支持和思考信息支持。

例如，当前 DeepSeek 配置可以返回如下能力描述：

```json
{
  "thinking_modes": ["auto", "enabled", "disabled"],
  "reasoning_efforts": ["low", "high", "max"],
  "streaming": true,
  "reasoning_content": true
}
```

页面据此生成选项。关闭思考时清空并禁用思考级别，切换配置后恢复该配置自己的会话和控件状态。每条回复记录发送时的模式、级别和输出方式，用户后来调整控件不会改写历史回复的标签。

后端仍然独立校验请求。当前能力描述和适配器校验分别实现，因此测试枚举了已覆盖的七种型号及其公开组合，同时检查流式、非流式两条路径，防止页面允许选择的参数在后端被拒绝。

这里的 `reasoning_content: true` 表示接入链路具备接收和展示能力。某次响应是否真的有思考信息，还要看上游返回。页面只展示供应商实际返回的内容，不会根据正文推测或补写模型的隐藏推理过程。

## 六、把流式调用实现为有结束约束的事件处理

流式调用需要处理网络分片、协议帧和生成状态三个层次。一次 TCP 数据读取可能只包含半个中文字符，也可能一次包含多个 SSE 事件。按网络块直接切 JSON，容易在真实环境中出错。

公共传输内核先通过 httpx 的行解码处理字符边界，再按 SSE 空行组织事件，支持多行 `data:`、CRLF 和心跳行。解析后的供应商数据交给 `StreamState` 累积正文、思考信息、工具参数、结束原因和用量。

上层接收统一事件：

| 事件 | 含义 |
|---|---|
| `start` | 网关开始处理生成流 |
| `reasoning` | 追加实际返回的思考信息 |
| `content` | 追加回复正文 |
| `usage` | 更新可获得的 Token 用量 |
| `tool_call` | 提供组装并校验后的完整工具调用 |
| `done` | 提供完整响应、结束原因和用量 |
| `error` | 流中发生错误，客户端结束本次等待 |

正文和思考分别累积。页面将前者显示在回复正文中，后者放进同一回复块里的可折叠区域。完成时，`done.response` 携带完整消息，用于与增量结果校准。非流式响应也保留同样的正文和思考字段。

结束判断尤其关键：

- 收到 `[DONE]` 或连接关闭时，仍要检查是否存在认可的 `finish_reason`。
- `stop` 表示正常生成结束；`tool_calls` 表示模型要求工具调用；`length` 表示输出被截断，需要向用户说明。
- 内容过滤、网络异常等结束原因转换为失败，不能显示成正常完成。
- 结束后的异常增量、缺失结束原因、格式错误都按协议错误处理。
- 缺失的用量保持未知，不补成零；返回的缓存 Token 和推理 Token 单独保留。

MiniMax 还可能在流末尾返回完整 `message`。若把它再次追加，页面会出现重复正文。当前实现校验完整消息与已累积内容的前缀一致，只输出新增部分；不一致时报告协议错误。

取消同样贯穿整条链路：前端使用 `AbortController`，后端在 `finally` 中关闭上游生成器和 HTTP 流。对于已经输出内容的流，当前实现不自动重试，避免重复输出或重复产生工具调用。取消后的供应商计费行为仍由上游服务决定。

## 七、多轮上下文需要保留结构，工具调用需要完整组装

消息模型除 `role`、`content` 外，还保留 `reasoning_content`、`tool_calls` 和 `tool_call_id`。这些字段决定后续请求能否延续前一轮的协议上下文。

以工具调用为例，完整过程包含三步：模型输出 assistant 工具调用；调用方执行工具并生成带 `tool_call_id` 的 tool 消息；将相关历史再次交给模型生成结果。适配层应保留这些结构，而不能只留下页面上可见的一段文本。

流式工具参数可能以如下片段返回，以下仅示意 `arguments` 的拆分：

```text
片段 1：{"a":
片段 2：12,"b":
片段 3：30}
```

`StreamState` 根据工具索引累积调用标识、名称和参数。在确认 `tool_calls` 结束原因后，校验调用结构、唯一标识以及参数是否为合法 JSON 对象，再向上层发出完整 `tool_call`。截断的半段参数不会作为可执行工具调用暴露。

适配层的校验到这里结束。工具是否存在、参数是否满足业务 Schema、用户是否有权限，以及执行是否有副作用，都属于后续 ToolExecutor 的职责。当前验证脚本使用无副作用的本地整数加法验证调用与结果回传，网页不会自动执行任意业务工具。

当前前端将多轮上下文保存在浏览器内存，并按模型配置隔离。停止或失败时，已返回的部分内容保留展示，但不会作为完整成功回复自动加入下一轮历史。服务端会话持久化尚未实现。

## 八、错误需要同时检查 HTTP、业务码和生成结束原因

模型服务的失败可能出现在不同位置：HTTP 返回 401、429 或 5xx；HTTP 200 但响应体包含业务错误；或者已经输出部分内容，最终以异常原因结束。

当前适配层将这些情况归一为 `AUTH_FAILED`、`QUOTA_EXCEEDED`、`RATE_LIMITED`、`CONTENT_FILTERED`、`CONTEXT_LENGTH_EXCEEDED`、`TIMEOUT` 等错误。供应商自己的业务码由各自适配器解释，公共层负责安全提示和统一结构。

流式接口在发送响应头前先做本地参数校验。开始输出后出现的上游错误，则通过 `error` 事件通知页面，因为这时已经无法重新发送一个普通 HTTP 错误响应。

原始上游错误正文不直接返回给用户，也不直接写入日志。可记录的信息包括供应商、规范化错误码、状态和响应中取得的请求标识，方便排查，又避免错误对象意外携带凭据或用户输入。

## 九、分层验证，并为“通过”写清范围

当前验证分为三个层次：

**第一层：协议测试。** 使用 MockTransport 构造四家的响应，检查请求地址、认证头、参数转换、中文分片、工具参数组装、业务错误、超时、取消、断流和异常结束等情况。这些测试适合稳定复现难以主动触发的失败路径。

**第二层：数据库与应用集成测试。** 使用隔离的真实 PostgreSQL，检查凭据密文、配置增改和停用、主密钥重启读取，以及“配置 API → 数据库 → 网关 → 适配器”的完整调用路径。该层的模型服务仍然使用模拟响应。

**第三层：真实供应商调用。** 验证脚本读取数据库中保存的配置，覆盖文本、多轮、流式、工具调用及工具结果回传。缺少可用配置时记录 `BLOCKED`，不能由协议测试结果推断真实服务已经通过。

2026 年 10 月 23 日的项目记录如下：

| 供应商及型号 | 协议与集成测试 | 真实 API 结果 |
|---|---|---|
| DeepSeek / `deepseek-flash` | 通过 | 文本、多轮推理回传、流式、工具调用与结果回传通过 |
| GLM / `glm-5.3-flash`，Coding Plan | 通过 | 文本、多轮推理回传、流式、工具调用与结果回传通过 |
| MiniMax / 当前适配覆盖型号 | 通过 | 待验证，缺少已保存的可用配置 |
| Kimi / 当前适配覆盖型号 | 通过 | 待验证，缺少已保存的可用配置 |

对应后端自动化记录为 **102 项通过、无跳过**，Ruff 与前端构建也通过。DeepSeek、GLM 各用五次真实请求完成四类基础检查，其中工具调用包含生成调用和结果回传两次请求。

思考控件另有真实应用接口验证：DeepSeek 覆盖 low 流式、high 非流式、max 流式，以及关闭思考的两种输出方式；GLM 覆盖 low 流式、high 非流式和 max 流式。启用思考的请求取得非空思考信息，流式分片拼接与最终响应一致；DeepSeek 关闭思考后没有返回思考信息。

这些检查证明对应参数和响应链路能够工作，不能据此推断推理质量排名，也不能保证不同级别的 Token 用量单调递增。

配置页面还有单次连接测试，作用是检查已保存配置能否完成一次文本生成。保存成功、单次文本通过、完整接入验证通过，分别对应不同证据，产品提示应当保留这种范围信息。

## 十、沿着这层接口继续建设企业能力

目前已经落实的基础是：配置和凭据管理、四家独立协议适配、统一生成契约、流式与非流式输出、思考信息传递、工具调用结构，以及可复现的验证脚本。

接下来可以围绕这层接口继续扩展：

| 后续能力 | 建设位置与关注点 |
|---|---|
| 租户权限 | 配置查询与调用前校验租户归属、用户授权 |
| 凭据治理 | 外部密钥管理、主密钥轮换、访问审计 |
| 调用治理 | 并发配额、预算、限流、失败分类和明确的重试策略 |
| 会话与观测 | 服务端历史持久化、首字延迟、总耗时、用量和错误分布 |
| Agent 执行 | ToolExecutor 的权限与参数校验、执行结果回传、循环停止条件 |

新模型接入时，可以沿用同一套步骤：确认具体型号和套餐协议，更新适配器与能力描述，补齐正常和异常协议测试，最后通过保存的配置执行真实调用。每一次“已支持”的结论，都对应到型号、参数组合、调用场景和验证记录，后续维护就有了明确依据。
