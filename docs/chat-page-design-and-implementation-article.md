# 企业级 Agent 平台建设：对话页面的设计与实现

模型接入层负责把请求发出去、把结果取回来，对话页面负责让用户理解这次调用发生了什么。

模型正在思考还是已经开始回答？一段回复是否完整结束？切换模型后，下一轮会带上哪些历史？代码复制得到的是原文还是页面里的高亮标签？手机屏幕变窄后，输入框还能不能正常使用？这些问题都会影响用户对平台的判断。

Begin Agent 的对话页面围绕模型配置、生成参数、消息内容和输入操作组织界面，使用 Vue 3、TypeScript 和原生 Fetch 实现。本文沿着页面结构、状态管理、内容渲染、响应式布局与验证流程，说明当前实现中的设计选择。

**本文对应 2026 年 10 月 23 日的代码与已有验证记录。** 当前页面是单页对话工作台，支持按模型配置隔离浏览器内存中的会话；服务端历史持久化、完整租户权限和业务工具执行仍需后续建设。模型接入层的设计可结合上一篇[《模型对接的设计与实现》](./model-integration-design-and-implementation-article.md)阅读。

## 一、围绕一次对话安排页面结构

页面从上到下分为四个区域：

| 区域 | 承担的操作与信息 |
|---|---|
| 顶部栏 | 产品标识、当前工作台定位、新对话 |
| 模型与设置区 | 选择已保存配置、新增或编辑配置、调整思考和输出参数 |
| 消息区 | 用户输入、模型回复、思考信息、用量和异常状态 |
| 输入区 | 编辑消息、发送、停止生成、必要提示 |

模型配置表单按需展开，放在模型设置与消息区之间。表单有独立滚动范围，关闭后把空间还给对话。

桌面端直接显示思考模式、思考级别和流式开关，便于反复调整。手机端则把这些参数收进“对话设置”，摘要仍显示当前状态。模型选择、新增模型和配置按钮保留在同一行，方便完成最常用的操作。

## 二、把一次模型回复放进一个完整卡片

一次模型回复会产生多种信息：模型名称、请求参数、思考内容、正文、Token 用量，以及可能出现的错误。如果这些信息散落在不同气泡里，用户很难判断它们属于哪一次调用。

当前页面使用一个完整的 assistant 卡片，内部顺序如下：

```text
回复卡片
  ├─ 模型名称与总 Token
  ├─ 本次请求参数摘要
  ├─ 可折叠的思考信息
  ├─ Markdown 正文
  ├─ 输入、输出、思考 Token
  └─ 停止、截断或失败提示
```

正文和思考信息可以独立更新，但始终属于同一条回复。即使先返回思考内容、随后返回正文，用户也能连续阅读这次生成过程。

用户消息靠右显示，保留原始文本；assistant 回复使用较宽的卡片，适合阅读长文、表格和代码。消息列表最大宽度为 1200px，输入区内容最大宽度为 900px，避免大屏上出现过长的阅读行。

承载这些内容的数据结构也保留了生成状态，下面是当前类型的核心部分：

```ts
interface ChatMessage {
  role: "user" | "assistant"
  content: string
  reasoning_content?: string
  reasoning_open?: boolean
  pending?: boolean
  settings?: GenerationOptions
  usage?: Record<string, number>
  error?: string
  incomplete?: boolean
}
```

`content` 保存回复原文，`reasoning_content` 保存上游实际返回的思考信息，`pending` 表示生成尚未结束，`incomplete` 表示当前内容不能作为完整成功回复使用。展示状态和原始内容放在一起，便于在中断、重绘和后续请求之间保持一致。

## 三、按模型配置管理会话和生成参数

页面选择的是一份已保存配置，标识为 `profile_code`。同一供应商可以有不同型号或不同套餐配置，前端需要按具体配置隔离上下文。

当前实现用两个内存 Map 分别保存消息与生成选项：

```ts
const conversations = new Map<string, ChatMessage[]>()
const profileOptions = new Map<string, GenerationOptions>()
```

切换配置时，先保存上一份配置的消息和参数，再恢复目标配置的状态。这样可以在两个模型之间来回切换，不会把它们的历史直接混在一起。生成过程中禁用模型切换和新对话，避免正在返回的数据写进另一个会话。

发送时还会复制一份当前参数，存入 assistant 消息：

```ts
const settings = { ...generation }
```

后续即使用户把思考级别从 high 改成 low，之前回复的参数摘要仍显示发送时的 high。这份快照让历史内容具备基本的可解释性。

参数选项由服务端返回的型号能力驱动。页面根据 `thinking_modes`、`reasoning_efforts` 和 `streaming` 生成控件；关闭思考后，清空并禁用思考级别。停用配置时，页面明确提示“已停用”，并阻止发送。

这些会话目前只存在于浏览器内存中，刷新页面会丢失，也不支持跨设备恢复。保存或修改模型配置后，当前实现会清理该配置的已有对话，避免配置已经变化却继续沿用旧上下文。后续接入服务端会话时，需要进一步明确会话标识、配置版本和历史迁移规则。

## 四、发送流程要覆盖等待、输出和异常结束

一次发送从本地状态开始：检查输入与配置是否可用；追加用户消息；构造请求历史；插入空的 assistant 卡片；创建 `AbortController`；再向后端发起请求。

页面根据流式开关选择 `/api/v1/chat/stream` 或 `/api/v1/chat`。非流式等待完整 JSON，界面显示“等待完整回复”；流式则不断更新同一个 assistant 对象。

前端接收的是后端整理过的事件协议：

| 事件或结果 | 页面行为 |
|---|---|
| `reasoning` | 追加到思考区域 |
| `content` | 追加到正文 |
| `usage` | 更新用量 |
| `done` | 用完整响应校准正文、思考和用量 |
| `error` | 保留已收到内容，标记失败并结束等待 |
| `finish_reason=length` | 提示达到输出上限，回复不完整 |
| `finish_reason=tool_calls` | 提示模型请求了工具，当前页面未执行工具 |

`consumeStream` 使用 `TextDecoder` 持续解码字节，将未完整的事件留在缓冲区，按空行分割后读取 JSON。它面向服务端输出的单行 `data:` 格式；供应商原始 SSE 的多行数据、心跳和协议差异，由后端适配层处理。

流关闭后还要检查是否收到带完整响应的 `done`。未收到时显示连接中断，避免网络断开后留下一个看似已经成功的回复。

停止按钮触发 `AbortController.abort()`。捕获取消异常后，页面显示“已停止生成”，保留当前正文和思考信息。在 `finally` 中解除忙碌状态、释放读取器，让用户能够继续操作。

下一轮请求构造历史时，只保留没有错误且完整的消息，再提取协议所需字段：

```ts
const requestMessages = messages.value
  .filter(m => !m.error && !m.incomplete)
  .map(m => ({
    role: m.role,
    content: m.content,
    ...(m.reasoning_content
      ? { reasoning_content: m.reasoning_content }
      : {}),
  }))
```

因此，界面保留的失败片段不会自动以完整 assistant 回复的身份重放给模型。卡片上的参数摘要、折叠状态等展示字段也不会进入请求。

当前收到事件后会在 Vue `nextTick` 后滚动到底部。这种方式便于跟随生成，但用户向上阅读历史时也可能被拉回底部。后续长会话交互可以增加“接近底部才自动跟随”和“有新内容”提示。

## 五、Markdown 渲染保留原文，并约束生成的 HTML

模型正文常常包含标题、嵌套列表、表格和代码。当前页面将这一部分抽成 `MarkdownContent.vue`，由 `markdown.ts` 负责渲染，使用三个库分别处理语法、代码和 HTML 清理：

```text
原始 Markdown
  → markdown-it 解析
  → 自定义表格、代码块和链接渲染
  → highlight.js 处理代码高亮
  → DOMPurify 清理生成的 HTML
  → Vue 展示
```

初始化时关闭原始 HTML：

```ts
const markdown = new MarkdownIt({
  html: false,
  breaks: true,
  linkify: true,
})
```

随后对生成结果进行清理，禁止 `style`、表单和输入等标签或属性。外链附带 `noopener noreferrer`；图片在当前文本渲染器中只显示替代文字，不自动加载模型提供的远程地址。

页面支持标题、有序和无序列表、嵌套列表、引用、链接、行内代码、表格及列对齐。表格外包一层可横向滚动的容器，避免列数过多时把整页撑宽。

流式生成时，每次 `content` 更新都会重新计算 Markdown。未闭合的代码围栏也能展示，后续片段到达后继续更新。用于历史请求的始终是原始 Markdown 文本，渲染后的 HTML 只用于展示。

目前渲染是完整内容重新计算，尚未实现增量 Markdown 解析或消息虚拟列表。随着长文和长会话增加，需要通过性能测量决定是否引入批量刷新、已完成消息缓存等机制。

## 六、代码高亮与复制分别处理显示内容和原始内容

代码块包含语言标签、复制按钮和代码区域。当前实现同时支持围栏代码和缩进代码：已知语言使用指定高亮；没有语言标签时，在有限语言集合中尝试识别；未知语言使用转义后的纯文本。

代码超过 50000 字符时跳过高亮计算，仍然完整展示和复制。这个限制约束高亮开销，不能代替整个对话页面的性能治理。

复制功能保留一份代码原文数组，按钮只带块索引：

```ts
const index = env.codeBlocks.push(code) - 1
// 生成的按钮包含 data-code-index，点击时读取对应原文。
```

高亮会插入许多 HTML 标签，从显示 DOM 反推代码容易引入格式问题。直接复制原文可以保留缩进、空行、换行和特殊字符。

组件在根节点做点击委托，通过 `closest("button[data-code-index]")` 找到目标按钮，再读取当前渲染结果对应的代码。这样流式更新导致代码块重绘时，无需逐个重新绑定点击处理函数。

复制优先调用 `navigator.clipboard.writeText`；不可用或失败时，尝试临时 textarea 和传统复制。回退过程会恢复之前的焦点与选区。

只有复制操作实际成功，按钮才显示“已复制”；失败显示“复制失败，请重试”。隐藏的 `aria-live` 状态区域同步提供反馈。代码语言标签采用单行省略并保留 `title`，避免超长标签把工具栏和按钮挤变形。

## 七、响应式布局先分配高度，再处理宽内容

页面采用纵向 Flex：顶部和输入区保留自身空间，聊天区占用剩余高度并独立滚动。核心样式如下，省略了视觉装饰：

```css
.app-shell {
  height: var(--app-height, 100dvh);
  min-height: 0;
  display: flex;
  flex-direction: column;
}

.chat-card {
  min-height: 0;
  flex: 1;
  display: flex;
  flex-direction: column;
}

.chat-body {
  min-height: 0;
  flex: 1;
  overflow-y: auto;
  overflow-x: hidden;
}
```

这里的 `min-height: 0` 允许中间区域缩小。缺少它时，Flex 子项可能被内容撑住，最终把输入区挤出可见范围。

页面监听 `visualViewport.resize`，优先使用可见视口高度，否则回退到 `innerHeight`。组件卸载时移除监听并取消未完成请求。输入区还保留 `safe-area-inset-bottom`，页面不禁用用户缩放。

窄屏下另外处理三个问题：

1. 模型栏使用 `minmax(0, 1fr) auto auto`，让选择框收缩，两个操作按钮保留空间。
2. 680px 以下折叠生成参数，点击输入框时收起设置；输入框和下拉框使用 16px 字号，减少移动浏览器因小字号而自动放大的情况。
3. 长代码、宽表格在卡片内部横向滚动；相关 Flex、Grid 子项使用 `min-width: 0`，避免内容最小宽度撑开页面。

低于 500px 高度时，页面缩减头部和辅助内容，为消息与输入操作保留空间。模型配置表单也限制最大高度并自身滚动。

已有检查覆盖低高度浏览器视口，但这尚不等同于在真实手机上弹出软键盘、输入并收起键盘的完整测试。

## 八、控件一致性落实为共享变量和几何规则

模型下拉框、配置按钮、思考下拉框和发送按钮如果分别设置尺寸，很容易出现高度和底边不一致。Logo 若直接使用字母，也可能受字体基线影响而显得偏斜。

当前页面把单行控件规格集中到 `style.css`：

```css
:root {
  --control-height: 40px;
  --control-radius: 8px;
  --control-border: #cbd5e1;
  --control-background: #fff;
  --control-text: #172033;
  --control-focus: #60a5fa;
}
```

按钮、单行输入、下拉框和思考折叠标题都引用统一高度与圆角，媒体查询也不另设尺寸。多行输入框可以更高，复选框保持 16px；消息卡片、徽标等非控件元素可以保留自己的视觉规格。

按钮用 Flex 居中，Logo 改用 SVG 并在 Grid 容器内居中。模型选择框与旁边按钮按底边对齐；文本和图标依靠布局规则定位，减少局部偏移补偿。

规范同时给出可测量标准：同排控件底边差、Logo 中心偏差不超过 0.5 CSS px；焦点可见、禁用不可触发；加载文案保持单行。测试时读取元素边界与计算样式，和截图一起检查。

完整规则保存在[前端开发规范](./frontend-standards.md)，`web/AGENTS.md` 将它接入每次前端变更流程。

## 九、配置操作也需要明确的状态约束

配置保存和连接测试耗时期间，如果还能编辑字段或切换配置，用户就难以判断结果对应的是哪一份输入。

当前实现使用 `configBusy` 和 `configAction` 管理操作状态：忙碌时锁定表单、启用勾选和相关导航，阻止重复提交，显示“保存中…”或“测试中…”。无论成功还是失败，都在 `finally` 中恢复操作。

API Key 编辑框不回显已有值，留空表示保留原密钥。关闭配置表单或保存成功后，清空本次输入的密钥。

状态文案也需要准确。“已保存”只说明配置已入库；连接测试通过后，提示只针对已保存配置的一次文本调用，不扩大为流式、多轮和工具调用全部通过。模型停用则提示启用或切换，避免引导用户无谓地重填密钥。

这些约束同样用于对话：空输入不能发送，生成中显示停止，失败保留内容，截断给出说明。控件状态与后台正在执行的操作相对应，页面才容易理解。

## 十、把前端验收分成自动检查和浏览器检查

当前项目使用统一入口执行前端检查：

```bash
npm --prefix web run check
# 或在项目根目录执行
make web-check
```

入口覆盖功能测试、UI 规则检查器测试、源码样式检查、Vue/TypeScript 类型检查和生产构建。

UI 检查器解析 Vue 模板和 CSS，收集控件类名，检查单行控件私设高度、圆角、局部变量覆盖，以及模板内联尺寸。检查器本身也有违规样式的反例测试，避免规则失效后仍显示通过。

静态分析无法证明实际文字对齐、遮挡和溢出都正确，因此规范要求界面变更追加浏览器验收，并保留几何记录与截图。

2026 年 10 月 23 日的整页检查记录为：**21 项自动测试通过**，包括 15 项页面和 Markdown 功能测试、6 项 UI 规则检查器测试；源码规则检查、类型检查和生产构建通过。

浏览器覆盖六种视口：

| 视口（CSS px） | 主要检查场景 |
|---|---|
| 320 × 800 | 极窄屏幕，模型栏与按钮收缩 |
| 390 × 844 | 手机竖屏、消息与代码展示 |
| 768 × 1024 | 平板尺寸 |
| 1280 × 720 | 桌面布局与完整操作 |
| 844 × 390 | 横屏低高度 |
| 390 × 360 | 可见区域进一步收缩 |

六种视口记录均满足页面无横向溢出和额外外层纵向滚动，输入区在视口内。可见单行控件高度为 40px、圆角为 8px，同排底边差和 Logo 中心偏差均为 0。

边界内容包括 128 字符模型名、六列表格、长代码和超长语言标签。桌面与手机还实际操作了停止、HTTP 错误、流中错误、截断、保存和验证锁定，以及思考区域折叠。

这些证据需要分别理解：

- 整页浏览器验收使用实际页面和模拟 API，验证布局及异常状态。
- 此前真实模型调用验证了从对话页到后端、供应商再回到页面的链路。
- 精确复制原文与复制失败回退由组件测试断言；浏览器检查确认按钮反馈，未宣称通过系统剪贴板粘贴读取验证。
- 已添加 GitHub Actions 工作流文件，已有记录未包含云端工作流运行通过的结论。

本文仅整理代码和已有记录，没有修改前端代码，也没有重新执行浏览器验收或外部模型调用。

## 十一、下一步围绕会话规模和协作继续演进

当前 `App.vue` 集中了配置、会话、请求和页面布局，Markdown 已单独拆分。随着功能增加，可以将流式消费、配置操作、会话状态拆为 composable，再拆分模型工具栏、消息卡片和输入组件，保留现有协议边界和测试。

继续建设时，有几项明确工作：服务端会话持久化支持刷新和跨设备恢复；长会话需要评估虚拟列表与渲染开销；自动滚动需要尊重用户阅读位置；真实移动设备需要补齐键盘与安全区域测试；租户协作则需要权限、配置归属和审计。

这些扩展可以沿用当前的设计约束：一次回复完整呈现，历史保留发送时的参数，异常结果有明确标记，原始内容与渲染结果分开管理，前端每次变更都有可复查的检查记录。
